# Разрешения IPv4 и IPv6 для каждого клиента

Статус: реализовано в рабочей ветке `codex/client-ip-families`, **не входит в
опубликованный 0.1.2**. Серверные проверки на Alpine/OpenRC и настоящих AWG-туннелях
пройдены; пользователь также подтвердил ручной цикл включения, блокировки и
восстановления IPv6, прямой IPv6 при запрещённом IPv4 и ожидаемое ограничение DNS.
Полная матрица способов импорта и DNS AmneziaVPN на обеих ОС ещё не закрыта.

## Поведение

Это разрешения трафика внутри VPN, а не изменение адресов или маршрутов клиента.
Переключатели заменяют «Клиент включён»; Home/Guest остаётся отдельной настройкой.
IPv4/IPv6 находятся в сворачиваемом разделе **«Настройки доступа»**, закрытом
по умолчанию. Текущий режим виден под именем клиента и при закрытом разделе.
«Диагностика» остаётся отдельным разделом только для чтения. Обновление карточек
сохраняет открытые разделы и фокус переключателя; бейдж Home/Guest показывает
группу независимо от разрешённых семейств, в том числе при отключённом клиенте.

| IPv4 | IPv6 | Результат |
|---|---|---|
| Вкл. | Вкл. | Обе семьи разрешены |
| Вкл. | Выкл. | Только IPv4 |
| Выкл. | Вкл. | Только IPv6, с ограничениями DNS и доступности сайтов ниже |
| Выкл. | Выкл. | Клиент отключён, peer удалён из работающего AWG |

Новый клиент получает обе разрешённые семьи, если сервер поддерживает IPv6.
На IPv4-only сервере переключатель IPv6 неактивен и сопровождается пояснением.

- Адреса, ключи, DNS, `AllowedIPs` и `vpn://` остаются прежними во всех четырёх
  состояниях. При изменении только разрешений повторный импорт не нужен.
  После полного отключения peer или перезапуска сервера восстановление связи
  может ждать нового handshake. Это не мгновенная смена маршрута приложения;
  в полевом тесте существующий клиент восстановился сам, без повторного импорта.
- Пока хотя бы одна семья разрешена, peer остаётся в AWG. Его серверные
  `AllowedIPs` также сохраняют оба адреса: фильтрация делается firewall,
  а не изменением криптографической привязки адресов.
- Запрещённая семья блокируется **от клиента и к клиенту**: интернет, Home ↔ Home,
  серверные службы и уже установленные соединения. Правила срабатывают до
  разрешений Home и `established,related` в собственной таблице `awg_easy_3`.
- Переключатель не создаёт direct-маршрут и не управляет сетью ОС пользователя.
  Раздельное туннелирование, исключённые приложения и отключение VPN находятся
  вне контроля панели. Это не клиентский kill switch.
- Фильтрация относится к **внутреннему трафику туннеля**. Внешний UDP-транспорт
  AWG может оставаться IPv4 даже у IPv6-only клиента; это необходимо для туннеля
  и не означает разрешённый IPv4-интернет внутри него.
- Handshake и служебные счётчики AWG не являются доказательством разрешённого
  пользовательского трафика конкретной семьи. Диагностика остаётся агрегированной.
- Чужие контейнеры, интерфейсы и правила не меняются. WARP, NAT64 и DNS-исключения
  для обхода выключенной семьи не добавляются.

## Как не потерять панель

Панель слушает только свои внутренние IPv4 и IPv6, не `0.0.0.0`/`::` и не
публичный адрес. Под списком клиентов есть раскрываемая справка и ссылки
«Панель по IPv4» / «Панель по IPv6» с фактическими адресами сервера.

Нельзя выключить семью, через которую **этот клиент сейчас обращается к панели**,
перевести этот клиент в Guest или удалить его. Сервер определяет клиента по
адресу TCP-соединения, не доверяя `X-Forwarded-For`. Сначала откройте панель по
другой разрешённой семье или подключитесь через другой Home-профиль. При переходе
между IP-адресами потребуется снова войти: браузер хранит cookie отдельно для
каждого адреса.

Должен оставаться хотя бы один Home-клиент с хотя бы одной разрешённой семьёй.
Это проверка конфигурации, а не гарантия, что запасное устройство сейчас в сети.
Не помещайте перед панелью прокси: он скроет реальный адрес клиента и ослабит
защиту текущего пути. Публичный reverse proxy проектом не предусматривается.

## DNS: существенное ограничение клиента

Двухстековый `.conf` уже содержит IPv4- и IPv6-резолверы AdGuard DNS. Его полный
текст включён и в `vpn://`. Но отдельные поля `dns1`/`dns2` формата AmneziaVPN
содержат IPv4-пару для совместимости.

При проверке исходников AmneziaVPN обнаружено, что
[`NativeServerConfig::getDnsPair()`](https://github.com/amnezia-vpn/amnezia-client/blob/dddc18129926206a695175d6b9941c39f9c730e0/client/core/models/selfhosted/nativeServerConfig.cpp#L37)
проверяет поля DNS именно как IPv4; Android-путь создания интерфейса использует
`dns1`/`dns2`. Поэтому нельзя обещать, что IPv6 DNS из вложенного `.conf` будут
реально применены конкретной версией приложения.

**IPv6-only может оставить устройство без разрешения доменных имён**, даже если
прямое соединение с IPv6-адресом работает. Проверять надо DNS, фактически
применённые на устройстве, а не только наличие строк в экспортированном файле.
Простая замена `dns1`/`dns2` на IPv6 проблему надёжно не решает. Панель показывает
это предупреждение и не разрешает IPv4 DNS в обход запрета администратора.

Даже с рабочим IPv6 DNS IPv4-only сайты не заработают: NAT64 здесь нет.
Паузы при переборе DNS и семейств адресов зависят от клиентского приложения.

Discovery-ретранслятор сейчас работает по **IPv4**. Отключение IPv4 также исключает
клиента из mDNS/SSDP-ретрансляции и удаляет его временные записи запросов. Это не
реализация discovery по IPv6; обычный разрешённый Home IPv6-трафик остаётся.

## Состояние и API

Добавлены булевы `ipv4Enabled` и `ipv6Enabled`. При чтении старого состояния
включённые клиенты получают все доступные семьи, а отключённые остаются
отключёнными. Адреса, ключи и профиль сервера не перевыпускаются. Частично
записанная пара флагов или IPv6 без серверной поддержки отклоняются.

Формат состояния остаётся аддитивным, `version: 1`. API возвращает `enabled`
как логическое ИЛИ двух флагов, а также `ipv6Available`. При записи на диск
старое поле `enabled` специально равно `false` у частично ограниченного
двухстекового клиента: старый код, не знающий новых флагов, не должен при
ручном откате внезапно разрешить ему обе семьи. В новом коде флаги имеют
приоритет. **Откат на старую версию может полностью отключить таких клиентов
или остановить запуск, если не осталось совместимого Home-профиля**; это
безопасная остановка, а не обещание бесшовного downgrade.

Авторизованный `PATCH /api/v1/clients/:id` принимает один или оба новых флага.
Старое `{ "enabled": true/false }` означает явно включить все доступные семьи
или выключить все; смешивать старый параметр с новыми в одном запросе нельзя.
Ошибки безопасности имеют HTTP 409 и код `CURRENT_PANEL_PATH`, `LAST_HOME` либо
`IPV6_UNAVAILABLE`; в панели они переведены на пять языков.

`GET /api/v1/network` после авторизации возвращает только внутренние ссылки
панели. Ключей и паролей в этом ответе и списке клиентов нет.

## Что уже проверено локально

- Полный набор после исправлений Alpine и переноса настроек доступа:
  203 автоматических теста без ошибок и пропусков; проверен синтаксис
  shell-сценариев. Docker на локальном Windows-стенде недоступен; полный
  производственный Dockerfile затем собран на тестовом VPS.
- Автоматические тесты: миграция, четыре комбинации, неизменность экспортов,
  Home/Guest, отказ при самоблокировке/отключении последнего Home, откат после
  ошибки записи, проверка адреса сокета, два внутренних HTTP-listener и переводы.
- В WSL Ubuntu, **в отдельном network namespace**, настоящие nftables и TUN:
  82 проверки пакетов — обе семьи, оба направления, существующий conntrack/NAT,
  локальные службы, Home/Guest, пустые allow-наборы, IPv4-only сервер и
  незатронутые посторонние forwarding/таблица. WSL не становится поддерживаемой
  платформой установки; здесь она только изолированный стенд Linux firewall.
- В браузере на вымышленных данных: состояния переключателей, отключение и
  восстановление клиента, сообщение о самоблокировке, недоступный IPv6, все
  пять переводов и RTL. Вёрстка также осмотрена в локальном 390px-предпросмотре
  на русском и фарси. Это не тест Android или настоящего VPN.
- Для «Настроек доступа» добавлены проверки структуры HTML, независимого
  сохранения открытых разделов, возврата фокуса, отказа API и сбоя обновления
  списка после успешной записи. Новая вёрстка повторно проверена в браузере;
  на VPS не развёрнута, поскольку пользователь уже удалил тестовый сервер.

Воспроизведение пакетного теста на подготовленном Linux-стенде:

```sh
node src/test/helpers/ip-family-policies.js | sudo unshare --net \
  python3 src/test/helpers/verify-ip-families-linux.py
```

Скрипт откажется запускаться в основном network namespace. Зависимости теста:
Python 3, Node.js, `ip`, `nft`, `unshare`, `/dev/net/tun`. В контейнер приложения
дополнительные зависимости ради теста не устанавливаются.

## Полевой тест Alpine / OpenRC — 2026-08-31

На Alpine 3.23.5 / OpenRC выполнены сборка, миграция с runtime 0.1.2,
134 проверки двух настоящих AWG-туннелей, 82 дополнительные пакетные проверки
в изолированном namespace, защита последнего IPv6-only Home и повторная
перезагрузка ОС. Разные разрешения пережили перезапуск; штатная отложенная
проверка OpenRC завершилась один раз и не перезапустила VPN.

Исправлены найденные на минимальном хосте несовместимость `sysctl --system`,
отсутствие `/usr/local/sbin`, незагружаемый после reboot модуль TUN и ложный
статус `crashed` после окончания одноразовой задачи OpenRC. Подробности и границы
доказанного — в [отчёте Alpine](VPS_TEST_2026-08-31.ru.md).

Ручной тест с пользователем подтвердил IPv6-доступ, блокировку и восстановление
переключателем без переимпорта и переподключения VPN. Первоначальная недоступность
на Windows была связана с включённым режимом AmneziaVPN «только выбранные сайты»:
IPv6-маршрут в VPN отсутствовал. Отключение фильтра восстановило доступ без правок
сервера. Затем пользователь подтвердил прямое IPv6-соединение при запрещённом
IPv4; доменные имена в этом режиме не разрешались (`ERR_NAME_NOT_RESOLVED`).
Возврат IPv4 восстановил DNS и сайты. Это согласуется с описанным ограничением
клиента, но без отдельной фиксации фактически применённых DNS не устанавливает
его точный механизм. IPv4 на телефоне, через который оставался доступ к панели,
пользователь намеренно не отключал. Временный VPS после тестов удалён.

## Оставшаяся ручная проверка Android / Windows

Подойдёт временный Alpine Linux x86_64 KVM VPS с рабочими IPv4 и IPv6.
Использовать подготовленный тестовый образ, не обещать новую функцию в stable
до окончания проверки. Нужны два устройства и запасной Home-профиль.
Для базовой матрицы отключить раздельную маршрутизацию по сайтам/приложениям
и переподключить VPN: иначе проверяемый запрос может вообще не попасть на сервер.

1. Проверить чистую установку, Docker/Compose, внутренние адреса панели и
   сохранение настроек после перезапуска контейнера и перезагрузки ОС.
2. Проверить настоящий OpenRC-запуск и отложенную проверку обновлений;
   отключение/повторное включение `auto-update` не должно менять IP-флаги.
3. Импортировать профиль **один раз**, сохранить его контрольную сумму;
   перебрать обе семьи / только IPv4 / только IPv6 / обе выключены / обе включены.
4. В каждом состоянии проверить `curl -4/-6` или эквивалент, прямые IP, отдельные
   DNS-запросы по каждой семье и обычные доменные имена на Android и Windows.
   Отдельно записать версии AmneziaVPN и способ импорта `.conf`/`vpn://`.
5. Переключать во время передачи: запрещённая семья должна прекратить доставку
   и по старым соединениям. Проверить трафик в обоих направлениях и Home ↔ Home.
6. Проверить Guest → панель/соседи по обеим семьям, Home → внутренний IPv6 панели,
   защиту текущего пути, последнего Home и сохранение флагов при смене группы.
7. Сверить стороннюю инфраструктуру до/после; убедиться, что таблицы, порты и
   её соединения не изменены. Выключение семьи VPN не выключает её на VPS.
8. Проверить обновление с 0.1.2 с включёнными и отключёнными старыми клиентами:
   ключи/профили прежние, отключённые не ожили. Проверить повторное чтение и
   обновление уже частично ограниченных клиентов, затем чистое удаление.

Уже сообщённые пользователем результаты IPv6-only и восстановления DNS не нужно
считать непроверенными. Дополнительное покрытие при следующем тесте: фактически
применённые DNS и сравнение импорта `.conf` / `vpn://` на обеих ОС. Серверные
AWG-пробы в отдельных Docker-сетях не заменяют эти устройства и их путь через интернет.
