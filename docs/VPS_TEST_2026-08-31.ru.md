# Проверка IPv4/IPv6 и Alpine/OpenRC — 2026-08-31

## Результат и границы

Серверная часть новой функции проверена на временном Alpine VPS. Это локальная
ветка `codex/client-ip-families`, а не опубликованный релиз: **stable 0.1.2,
`master` и `latest` не изменялись**. Для выпуска ещё нужны настоящие Android и
Windows с AmneziaVPN, особенно фактически выбранные приложением DNS.

Два автоматических клиента использовали настоящие AWG-конфигурации, TUN и
шифрованные UDP-туннели в отдельных Docker network namespace на том же VPS.
Доступ в интернет проверялся через внешний сервис определения IP, DNS —
отдельными запросами к заданным резолверам каждой семьи. Это не имитация firewall,
но и не доказательство прохождения туннеля между физическими устройствами через
сеть оператора/домашний NAT.

## Стенд

- Alpine Linux 3.23.5, OpenRC, Linux 6.18.44-0-virt, x86_64 KVM.
- Один vCPU, около 1 ГиБ памяти, без swap; рабочие публичные IPv4 и IPv6.
- Docker 29.5.2 и Compose 2.40.3 установлены установщиком через `apk`, как и
  остальные недостающие рабочие зависимости. Git использован для получения
  проекта; Python — только внешний инструмент тестирования, не зависимость панели.
- Полный закреплённый производственный Dockerfile собран на VPS последовательно,
  без изменения исходников AWG или Node-зависимостей, без публикации образа.
- Контейнер приложения проверен из кода `43d35914`; последующие изменения
  относятся только к установщику, хостовому OpenRC-механизму, тестам и документации.

Пароли, ключи, `vpn://`, конфигурации клиентов, адрес тестового хоста и приватные
сырые логи в репозиторий не включены.

## Что пришлось исправить

1. **BusyBox sysctl.** Установщик останавливался на неподдерживаемом `--system`.
   Теперь применяется только `/etc/sysctl.d/99-awg-easy-3.conf` через `sysctl -p`.
   Посторонние sysctl-файлы повторно не загружаются.
2. **Минимальная файловая система.** `/usr/local/sbin` отсутствовал: панель уже
   работала, но глобальная команда ещё не могла установиться. Каталог теперь
   создаётся явно до копирования команды.
3. **TUN после reboot.** Однократного `modprobe tun` оказалось недостаточно:
   после первой перезагрузки Docker не смог восстановить контейнер из-за
   отсутствия `/dev/net/tun`. Добавлен собственный
   `/etc/modules-load.d/awg-easy-3.conf`. Вторая настоящая перезагрузка
   автоматически подняла TUN и здоровый VPN с прежним состоянием.
4. **Одноразовая задача OpenRC.** Проверка обновлений успешно завершалась, но
   оставалась отмеченной `crashed`. Теперь worker сохраняет код завершения
   в журнале и снимает собственную отметку работающего сервиса штатным `zap`;
   PID-проверка не позволяет затронуть заменивший его worker. После завершения
   статус — `stopped`, а включение в boot-runlevel сохраняется. Механизм `zap`
   описан в [руководстве OpenRC](https://github.com/OpenRC/openrc/blob/master/user-guide.md).

## Проверенные сценарии

- Стабильный runtime 0.1.2: созданы отдельные включённые Home и отключённый Guest;
  Home ↔ Home по IPv4 и IPv6 работает в обоих направлениях.
- Миграция на новый runtime: все серверные/клиентские ключи, адреса и настройки
  сохранены; ранее отключённый Guest не включился. Оба экспортируемых формата
  совпали с исходными. Старые профили дошли до обеих внутренних панелей.
- **134 проверки реальных AWG-туннелей**: оба протокола / IPv4-only / IPv6-only /
  выключено / восстановлено; Home ↔ Home, клиент → сервер и сервер → клиент,
  повторное использование UDP-потока с прежним conntrack, DNS обеих семей,
  внешний IPv4/IPv6 сервера, неизменность экспортов и чужого Home-клиента.
- В режиме запрета исходящий локальный пакет также может быть отвергнут ядром
  сразу с `EPERM`, а не только таймаутом. Тест учитывает оба корректных результата.
- Защита текущего соединения панели по каждой семье: отключение, перевод в Guest
  и удаление текущего клиента отвергнуты даже с подставленным `X-Forwarded-For`.
- Guest не получает доступ к панели или Home; смена группы не сбрасывает
  ограничения семейств. Последнего IPv6-only Home нельзя отключить, удалить
  или перевести в Guest — три отдельные проверки.
- **82 дополнительные пакетные проверки** выполнены на ядре Alpine в отдельном
  network namespace: существующий conntrack/NAT, обе стороны, локальные службы,
  IPv4-only сервер и независимые правила/forwarding. Сеть хоста ими не заменялась.
- Разные флаги двух клиентов пережили рестарт контейнера и настоящую загрузку ОС:
  контрольная сумма состояния не изменилась, после запуска клиентов разрешённая
  семья работала, запрещённая — нет.
- Чужой контрольный контейнер и сервис мониторинга провайдера сохранились;
  отдельная синтетическая nftables-таблица пережила перестройку политики панели
  и её рестарт. Такая неперсистентная тестовая таблица сама по себе не обязана
  переживать reboot ядра.
- OpenRC через штатные пять минут выполнил ровно одну проверку stable. VPN
  не перезапускался и не заменял тестовый образ; worker закончил со статусом
  `stopped`, без ложного `crashed`. `auto-update disable/enable` и отдельный
  `auto-update run` не изменили сохранённые разрешения.
- Финальное удаление из постороннего рабочего каталога убрало только данные
  панели, её интерфейс/правила, команду, sysctl/modules-load файлы и OpenRC hook.
  Чужой контрольный контейнер, отдельная таблица и мониторинг провайдера остались.
  Последующая чистая установка со всеми исправлениями завершилась успешно;
  затем на неё повторно поставлен приватный кандидатный runtime.
- После испытаний удалены только созданные тестом probe/sentinel контейнеры и
  синтетическая таблица. Для ручной проверки созданы отдельные Home-профили
  телефона, ПК и резервный Home; старые миграционные fixtures сохранены приватно.
- Полный локальный набор после исправлений: **198 тестов**, ошибок и пропусков
  нет; shell-синтаксис установщика и библиотеки обновлений проверен отдельно.

Полное отключение удаляет runtime peer. Его возврат или рестарт сервера может
потребовать нового handshake; в тесте существующие клиенты восстановились сами,
без повторного импорта или принудительного перезапуска приложения. Это не
обещание мгновенного восстановления при любых состояниях клиентской сети.

## Что остаётся пользователю

1. Импортировать разные профили на Android и Windows и записать версии AmneziaVPN
   и способ импорта (`.conf` / `vpn://`). Один профиль не делить между устройствами.
2. Повторить четыре положения переключателей, доступ Home ↔ Home и вход в панель
   через фактический IPv6. Управлять тестируемым профилем со второго устройства.
3. Отдельно проверить прямой IPv6 и разрешение доменных имён в IPv6-only.
   Серверные IPv6 DNS-запросы успешно проходят, но AmneziaVPN может использовать
   только IPv4 из `dns1`/`dns2`. Наличие IPv6 DNS в `.conf` не доказывает их
   применение приложением. IPv4 DNS в обход запрета не разрешается.

Нет NAT64, WARP или управления direct-трафиком за пределами VPN. Проверка этого
этапа не снимает прежних клиентских ограничений multicast discovery.
