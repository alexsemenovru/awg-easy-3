# Полевой раунд Основного узла и Ячейки — 8 октября 2026

Статус: **проверка компонентов, не релиз**. Две временные VPS: ALT Server 10.4
(Основной узел) и Alpine 3.23.6 (Ячейка). Рабочая установка владельца не
затрагивалась. Стенд использовал отдельные AWG-интерфейсы, адреса, порты,
таблицы nftables и каталог состояния; Docker и пользовательские профили на
эти VPS не устанавливались. SSH host key каждой машины был закреплён до
передачи учётных данных. После раунда эти VPS можно удалить.

## Подтверждено на реальных Linux/VPS

1. Одноразовое v2-приглашение создало временный AWG-пир. Ячейка
   зарегистрировалась только через внутренний TCP-адрес этого канала;
   состояние приглашения перешло в `consumed`, а постоянная идентичность
   Ячейки сохранилась. Отсутствие `/dev/net/tun` на чистой Alpine требовало
   загрузить модуль `tun`.
2. Постоянный AWG-путь поднялся на обеих ОС. До его проверки запрос управления
   был отклонён. После проверки временный пир удалён, а Ячейка сохранила
   постоянную идентичность и закрыла временный интерфейс.
3. Подписанные `poll → apply → ack` прошли внутри постоянного AWG без TLS:
   применена и подтверждена ревизия 1. При остановке служебного listener
   ревизия 2 не применялась и прежняя ревизия оставалась на Ячейке; после
   запуска listener ревизия 2 была применена и подтверждена. Это была
   **пустая тестовая настройка** — применение реальных клиентов/маршрутов
   этим прогоном не проверялось.
4. После отдельных перезагрузок Alpine и ALT новые boot ID подтвердили
   реальный reboot. Ручное восстановление из журналов владения заново
   создало постоянные AWG-интерфейсы и правила; после восстановления
   служебный обмен ревизией 2 снова прошёл. Автоматический запуск при boot
   ещё не реализован и этим тестом не подтверждён.
5. На Alpine при административном выключении AWG-интерфейса Linux выбирал
   публичный default route к **внутреннему** адресу контроллера. Добавлено
   отдельное правило nftables `output daddr <внутренний адрес> drop`, не
   зависящее от имени интерфейса. При повторном тесте `tcpdump` на внешнем
   интерфейсе показал **0 исходящих TCP-пакетов** к служебному адресу.
   Интерфейс был восстановлен, дальнейший обмен работает. Это проверка
   служебного пути, не доказательство маршрутизации пользовательского трафика.
6. В ядре nftables readback группирует правила по цепочкам, хотя установка
   смешанной пачки допускается. Снимки bootstrap-политик приведены к
   readback-порядку; прежний вариант не проходил точную проверку владения.
   `awg showconf` также сообщает автоматически назначенный listen-port
   клиента. Теперь отсутствие порта в желаемой конфигурации допускает это
   значение, а явно заданный порт по-прежнему проверяется строго.

## Публичная DHT: отдельный эксперимент

На обеих VPS был закреплён `bittorrent-dht@11.0.12`. Опубликована только
одноразовая подписанная тестовая BEP 44-запись без адресов пользователей,
профилей, команд или backup. Между площадками успешно проверена подпись
ревизии 1. Новый процесс и UDP-порт опубликовали ревизию 2; Ячейка получила
и проверила новую ревизию. При запуске читателя без публичных bootstrap-
адресов, но с известным прямым контактом, первый поиск был пустым, следующий
нашёл запись. Это показывает восстановление через **известный контакт**, но
не доказывает обнаружение с нуля при блокировке всех точек входа. На коротком
прогоне издатель использовал около 80 МиБ RSS; измерений длительной работы,
нагрузки при реальном VPN-трафике и точного UDP-бюджета пока нет.

## Локальная регрессия и границы результата

После исправлений `pnpm -C src test`: 507 тестов, 477 успешных, 30
пропущенных по платформенным условиям, 0 ошибок. Продуктовый installer/CLI/UI
для Ячеек, автоматический boot/recovery, доставка топологии, реальные
пользовательские правила Home/Guest/GeoIP через обе VPS, резервный DHT-канал
управления и полноценная отмена изменений ещё не прошли end-to-end проверку.
Полевые скрипты вручную проводили постоянный AWG-путь и использовали пустую
тестовую настройку. Они не являются инсталлятором и не должны попадать в
релиз как готовая функциональность.

Следующий этап — соединить проверенные строительные блоки в продуктовый
жизненный цикл Ячейки, затем снова испытать чистую установку, сбои и
настоящий пользовательский трафик на двух временных VPS. До этого большой
релиз Основных узлов и Ячеек объявлять нельзя.
