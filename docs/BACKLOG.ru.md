## 2026-08-27 — индикация после переключения профилей на одном телефоне

Статус: точная причина наблюдения не установлена; крайние случаи расчёта
исправлены в рабочей ветке, нужен повторный тест. Не считать доказательством постороннего
подключения или подтверждённым дефектом расчёта скорости.

### Как воспроизвести

1. Импортировать на телефон профиль `Home admin`, сохранённый после установки
   панели в сохранённых сообщениях мессенджера. Другие устройства этим профилем
   в момент проверки не пользовались.
2. Подключиться через `Home admin`, войти в панель и создать профиль `Honor 50`.
3. Сразу переключить AmneziaVPN на том же телефоне с `Home admin` на `Honor 50`.
4. Снова открыть панель.

Наблюдение: оба профиля отображались активными; у уже не используемого
`Home admin` панель показывала передачу примерно **200 байт/с**, по сообщению
пользователя. Точная единица интерфейса, направление, длительность показания
и время после переключения не зафиксированы — уточнить при повторном тесте.

### Что проверить при возобновлении работ

- Записать время переключения и последовательность показаний обоих профилей
  до и после него, включая обновление страницы панели.
- Сопоставить статус и скорость в UI с ответами API, серверными счётчиками
  RX/TX и временем последнего handshake отдельно для каждого peer.
- Проверить окно определения «в сети», интервал опроса и усреднения скорости:
  отличить недавнюю активность от продолжающейся передачи.
- Проверить сброс предыдущих выборок, корректную привязку счётчиков к peer,
  отображение устаревших данных и единицы bit/s против byte/s.
- При наличии реального роста счётчиков выяснить направление и природу
  трафика: остаточная передача, служебные пакеты или иной источник. Это
  гипотезы для проверки, а не установленная причина.
- Проверить, что после прекращения трафика скорость становится нулевой,
  а статус меняется по документированному тайм-ауту; при необходимости
  уточнить подписи UI, чтобы недавний handshake не означал гарантированное
  подключение устройства прямо сейчас.

Стабильный релиз не изменён; рабочие доработки описаны в срезе выше.

## 2026-08-28 — отдельное управление IPv4 и IPv6 клиента

Статус: идея для будущей версии, реализация не начата.

- Вместо «Клиент включён» рассмотреть два переключателя: IPv4 и IPv6.
- По умолчанию включать обе семьи, если сервер поддерживает обе. При отсутствии
  работоспособного серверного IPv6 показывать его недоступность с объяснением,
  а не обещать клиенту неработающее подключение.
- Четыре состояния: обе семьи, только IPv4, только IPv6, обе выключены
  (клиент отключён). Отобразить состояние явно; Home/Guest остаётся отдельным.
- Отключение обеих семей должно удалять peer из runtime. Сохранить защиту
  от отключения последнего доступного Home-клиента и потери доступа к панели.
- Согласовать адреса, AllowedIPs, DNS, nftables, discovery и экспорты профилей.
  У IPv6-only Home должен оставаться путь к панели и DNS через IPv6.
- Не путать отключение семьи внутри VPN с блокировкой её прямого выхода через
  провайдера: отдельно определить и проверить защиту от обхода туннеля.
- Изменение серверной политики не переписывает импортированный профиль в
  AmneziaVPN. Проверить, когда нужен повторный импорт, и явно сообщать об этом.
- IPv6-only не обещает доступ к IPv4-only сайтам без отдельного механизма
  трансляции. NAT64/DNS64 автоматически в объём этой задачи не включать.

## Ранее согласовано — случайный UDP-порт при чистой установке

Статус: реализовано в рабочей ветке; до релиза нужна проверка на VPS.

- Выбирать один случайный свободный UDP-порт из высокого диапазона вместо
  стандартного `51820`. Выбран диапазон 20000–60000, исключая 51820.
- Сохранить ручной выбор и проверки конфликтов с инфраструктурой VPS.
- Показывать выбранный порт после установки и включать его в профили клиентов.
- Обычное обновление сохраняет порт; новая чистая установка выбирает новый,
  если пользователь не задал его явно.
- Диапазон слушающих портов и индивидуальные порты клиентов не планируются.
  Смена порта не является гарантией защиты от DPI или блокировки IP.

## 2026-08-28 — автоматическое обновление после загрузки ОС

Статус: добавить в планы; автоматический режим требует доработки update.
Рекомендация: явная отключаемая опция установщика; значение по умолчанию
согласовать при внедрении, не включать скрытно на существующих установках.

### Лёгкий механизм запуска

- После успешной установки и проверки работоспособности регистрировать
  штатное задание ОС для одного запуска обновления после каждой загрузки.
- На системах с systemd использовать timer с OnBootSec и oneshot service:
  отдельный постоянно работающий демон или контейнер не нужен.
- Сначала позволить штатно подняться текущему VPN, затем с небольшой задержкой
  проверить обновления. Не блокировать загрузку ОС или старт VPN ожиданием
  GitHub, реестра образов или сети. Возможный краткий разрыв при замене версии
  описать пользователю.
- Наличие network-online.target не гарантирует доступ к GitHub/GHCR:
  нужны ограниченное время ожидания и обработка отсутствия сети.
- Для OpenRC и других уже поддерживаемых ОС отдельно оценить штатный механизм.
  Не устанавливать systemd, cron или новый демон только ради этой функции;
  если лёгкого проверенного варианта нет — сообщить, что автообновление на
  этой ОС пока недоступно, оставив ручную команду.
- Это обновление при загрузке, не периодическое: без перезагрузок новые
  релизы сами по себе не устанавливаются.

### Безопасность обновления — до включения автозапуска

- Текущая команда последовательно делает git pull --ff-only, заменяет
  управляющий скрипт, выполняет compose pull и compose up -d. Её нельзя
  считать готовым безопасным unattended-обновлением без дополнительных проверок.
- Использовать только опубликованные стабильные совместимые релизы, а не
  произвольный новый коммит master или prerelease. Механизм выбора/проверки
  согласованного комплекта скриптов, Compose и образа определить при реализации.
- Не пересоздавать контейнер, если рабочая версия не изменилась.
- Сохранять клиентов, ключи, пароль, порты и настройки. Никаких автоматических
  reinstall, сбросов или несовместимых обновлений состояния.
- Полностью получить и проверить новую версию до замены рабочей. При сбое
  загрузки оставить рабочую установку; при неуспешном healthcheck после замены
  предусмотреть согласованный откат образа и управляющих файлов.
- Исключить конкуренцию с ручным update, uninstall и reinstall; уважать
  намеренную остановку сервиса, не запускать его обратно без решения владельца.
- Журналировать версии и результат без паролей, ключей и vpn://-ссылок.
- Предусмотреть понятные включение/выключение и статус автозадания, а также
  его удаление при деинсталляции только для объектов AWG-Easy 3.
- Проверки: повторная загрузка, отсутствие сети, недоступный реестр, сбой
  нового контейнера, отсутствие обновлений, сохранение конфигов, ручной stop,
  параллельные команды и чистая деинсталляция.

Документация для проектирования:

- [Таймеры systemd (OnBootSec)](https://github.com/systemd/systemd/blob/main/man/systemd.timer.xml)
- [Готовность сети и запуск сервисов](https://systemd.io/NETWORK_ONLINE/)

Понятное DNS-имя панели исключено из текущего плана по просьбе автора.
Часть записей реализована в рабочей ветке согласно статусам выше.
