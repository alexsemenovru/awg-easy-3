# Наблюдения для будущих версий

## Решение 2026-10-01 — объединённый крупный релиз

Следующий публичный выпуск объединит систему «Основной узел / Ячейки» с
подготовленными изменениями интерфейса: новым фоном, подсказками и уведомлениями
об операциях. В этот же выпуск входит добровольная настройка TOTP с тремя
режимами входа: пароль, пароль + код, только код. Не выпускать эти изменения
отдельными косметическими патчами до согласованного крупного релиза.
В тот же состав входят сообщение о неверном пароле, исправление карточек,
ASCII-транслитерация имён скачиваемых `.conf`, выбор обнаруженного IP/другого
IP/домена в установщике и все связанные переводы. Ничего из этого списка
не откладывать «за борт» релиза Узлов и Ячеек.

Критерии перед публикацией: закончить и проверить узлы/ячейки по отдельному
плану, провести полевые проверки на двух VPS, проверить чистую установку,
обновление действующей панели с сохранением профилей и настроек, все режимы
входа с реальным приложением-аутентификатором, восстановление через SSH,
пять языков и мобильный интерфейс. При включении TOTP состояние получает
версию 3: старое ПО обязано отвергать его, а не молча сбрасывать защиту.
Поэтому отдельно проверить сценарии неудачного обновления, отката и сообщение
пользователю о несовместимости старого ПО с включённым TOTP. До этих проверок
не разворачивать эту ветку на рабочем ARN и не объявлять релиз готовым.

**Релизное описание клиентов (добавлено 2026-10-15):** поставить официальные
[AmneziaWG для Windows](https://github.com/amnezia-vpn/amneziawg-windows-client/releases)
версии 3.1.0+ и
[AmneziaWG для Android](https://github.com/amnezia-vpn/amneziawg-android/releases)
версии 3.1.x в начало рекомендаций для AWG-Easy 3, с импортом скачанного
`.conf`. В Windows пользователь проверил импорт профиля из нашей панели и
работу IPv4/IPv6; на Android ранее проверены подключение и доступ к панели
по обоим семействам на Honor 50. Это полевые наблюдения, не обещание
одинакового поведения всех ОС и сетей. AmneziaVPN оставить альтернативой
для `vpn://` и его дополнительных функций; отдельно предупредить о
наблюдавшейся на Android 5.0.2.1 недоступности внутреннего IPv6-адреса панели.
Перед публикацией повторить проверку актуальных версий, режимов IPv4-only и
IPv6-only, Home/Guest и переподключения после сна; коротко объяснить разницу
способов импорта. Публичный README текущего релиза менять вместе с
релизом Узлов и Ячеек, не выдавая новую рекомендацию за уже опубликованную.

## Актуальный порядок — согласовано 2026-09-13, дополнено 2026-10-19

1. Исторически планировался отдельный патч: уведомления об успешных операциях, согласованный фон BG3-soft,
   лаконичные подсказки (наведение/фокус/нажатие на телефоне), проверка подходящих
   обновлений AWG 3.x. Уведомления, фон и часть подсказок подготовлены локально;
   отдельный патч не выпускается — его состав включён в объединённый релиз выше.
2. **Основной узел и Ячейки**, включая распределённое обнаружение и резервную
   служебную ретрансляцию между всеми установками AWG-Easy 3. Единый защищённый
   протокол управления проектируется сразу для прямого и резервного путей;
   реализация поэтапная: сначала прямой канал, затем резервная сеть и испытания отказов.
   Согласованные детали:
   [NODES_AND_CELLS.ru.md](NODES_AND_CELLS.ru.md). Это проект будущей реализации,
   не функция текущей панели.
3. После завершения системы Ячеек — **минимизация данных на Ячейках**.
   Пересмотреть сохраняемые настройки, маршруты, журналы и временные файлы:
   оставлять только необходимое для работы и автономности, не сохранять
   человекочитаемые имена и готовую опись сети там, где достаточно технических
   идентификаторов. Проверить, что Ячейка не получает лишние сведения о клиентах
   других точек входа. Цель — уменьшить раскрытие метаданных при просмотре файлов,
   в том числе автоматизированном; не обещать защиты от владельца работающей VPS.
   Шифрование состояния и обязательная разблокировка Основным узлом не планируются.
4. **Backup/restore Основного узла** и восстановление управления Ячейками.
   Выделено из пункта №2 в отдельный этап; необходимые идентичности и границы
   полномочий учитываются при проектировании пункта №2. Детали сохранены в
   [NODES_AND_CELLS.ru.md](NODES_AND_CELLS.ru.md).
5. **Поддержка Windows Server**, после релиза
   системы Основного узла и Ячеек и работ над backup/restore. При проектировании
   проверить WSL containers (`wslc`) как возможный способ запуска Linux-контейнера
   без Docker Desktop. Выпуск GA от 2026-09-29 сам по себе не подтверждает
   поддержку Windows Server или пригодность для AWG: отдельно проверить
   доступность `wslc` на целевых Server 2022/2025, вложенную виртуализацию,
   входящий UDP, IPv4/IPv6, TUN, nftables, маршрутизацию, автозапуск и
   восстановление после reboot. Сравнить с Linux-VM под Hyper-V и обычным
   WSL2 с Docker Engine; решение принять по результатам испытаний.
   Источники: [анонс WSL containers](https://blogs.windows.com/windowsdeveloper/2026/09/29/wsl-containers-now-generally-available/),
   [WSL на Windows Server](https://learn.microsoft.com/windows/wsl/install-on-server).
6. **Поддержка Podman — после релиза Основного узла и Ячеек.**
   Отдельный вариант установки из того же OCI-образа и в том же репозитории;
   не включать в критический путь ближайшего релиза. Начать с rootful Podman
   на тестовой Linux VPS, проверить host-сеть, TUN, `NET_ADMIN`, nftables,
   маршрутизацию, автозапуск, обновление и восстановление после reboot.
   Сравнить Compose-провайдер с нативными Quadlet/systemd-службами; выбрать
   поддерживаемый путь по результатам испытаний. Rootless не обещать заранее.
   Не запускать Docker- и Podman-варианты одной панели одновременно на одной
   VPS: они конфликтуют за порты и сетевые интерфейсы. Эта работа не отменяет
   обязательную поддержку Windows Server из пункта 5.
7. **Исследовать возможный переход всего трафика на QUIC — после Windows Server.**
   Рассмотреть клиентский и межузловой трафик вместе: совместимость с AWG 3.x и
   существующими профилями, необходимость изменений клиентов, устойчивость к
   блокировкам, нагрузку на минимальные VPS и сложность эксплуатации. Это пока
   исследовательская задача, не решение заменять AWG или менять текущий
   служебный TCP-обмен внутри AWG до завершения предыдущих этапов.
8. **Рассмотреть DoQ внутри сети — дальнее исследование после пункта 7.**
   Оценить, нужен ли защищённый DNS-обмен между клиентами, Основным узлом и
   Ячейками для будущей маршрутизации: исключение DNS-утечек, совместимость
   клиентов и старых профилей, поведение при отказах и цена для минимальных
   VPS. DoQ решает задачу разрешения имён, но сам по себе не маршрутизирует
   IP-трафик. Этот пункт не возвращает в текущую разработку DNS-прокси,
   GeoSite или доменное имя панели; решение о реализации принять только после
   проверки пользы относительно существующей схемы.

Резервная сеть больше не является необязательным пунктом №4: она включена
в пункт №2 по последнему согласованию. См. [SUPPORT_NETWORK.ru.md](SUPPORT_NETWORK.ru.md).

GeoIP и стартовый экран выпущены в 0.1.6. Раздел «Актуальный план» от 2026-09-10
ниже оставлен как историческая запись; его будущие статусы не заменяют этот список.
DNS-прокси, GeoSite и доменное имя панели не возвращаются в план.

### Наблюдение 2026-09-09: тайм-аут IPv6-панели на Honor 50

- Пользователь сообщил `ERR_CONNECTION_TIMED_OUT` при переходе по корректной
  внутренней IPv6-ссылке. Оба семейства разрешены, AmneziaVPN работает в режиме
  «Все сайты».
- На изолированном стенде переход, страница и вход работают как с 0.1.3,
  так и с новым движком 0.1.4. Это не устанавливает причину на личном VPS.
- Для завершения диагностики нужны проверки IPv6-адреса/маршрута профиля,
  входящих пакетов, слушателя и nftables на действующей установке. До этого
  наблюдение не считается исправленным и не списывается на Android.

### 2. Microsoft Windows Server — обязательное направление

- Реализовать поддерживаемый путь установки и эксплуатации на Windows Server,
  а не ограничиться инструкцией для настольной Windows. Целевые версии ОС и
  требования к хосту согласовать при проектировании.
- Предложенная автором [ссылка Microsoft Store](https://apps.microsoft.com/detail/xp8cbj40xlbwkx)
  ведёт на Docker Desktop. По [официальному FAQ Docker](https://docs.docker.com/desktop/troubleshoot-and-support/faqs/windowsfaqs/#can-i-run-docker-desktop-on-windows-server)
  Windows Server им не поддерживается; не выбирать его основой серверной установки.
- Сравнить управляемую Linux-VM под Hyper-V и WSL2 с Docker Engine внутри Linux.
  [Microsoft описывает установку WSL2 на Windows Server 2022/2025](https://learn.microsoft.com/en-us/windows/wsl/install-on-server),
  но это ещё не подтверждение работоспособности нашей панели в такой среде.
  Окончательный вариант не выбран; поддержка Windows-хоста с Linux-средой
  исполнения и полностью нативный Windows-порт — разные объёмы работ.
- Проверить TUN, nftables, внешний UDP, IPv4/IPv6, Home/Guest и discovery,
  требования к виртуализации, включая вложенную виртуализацию на VPS.
- Установка, автозапуск без интерактивного входа, обновление, откат, диагностика,
  переустановка и удаление должны управляться понятными командами и не ломать
  чужие службы, контейнеры, сетевые настройки или удалённый доступ к хосту.
- Текущий выпуск остаётся Linux-only; прежний отказ установщика в WSL не
  снимается до реализации и проверки нового пути установки.

### 3. GeoIP через nftables — согласовано к реализации 2026-09-10

- Первый выпуск — только IP-фильтрация по странам, без DNS-прокси и GeoSite.
  Режимы: без фильтрации, блокировать выбранные страны, разрешать только выбранные.
  Поле стран с подсказками на пяти языках; хранить коды, не локализованные названия.
- Старые профили и DNS не меняются, переимпорт не требуется. Никакого direct.
  Классификация относится к IP-адресам, не к национальной принадлежности сервисов.
- Правила ограничены пересылаемым трафиком VPN ↔ WAN; Home-сеть, доступ к панели
  и чужая инфраструктура остаются под прежними правилами. Проверять обе семьи IP
  и запреты до разрешения established/related.
- Локально добавлены компилятор GeoIP-правил, автоматическое обслуживание DB-IP Lite,
  атомарное хранение и сериализованное применение обновлений (2026-09-10).
  Состояние базы и выбор стран доступны в локальном интерфейсе на пяти языках;
  изменение политики подключено к API. Впереди полноценная проверка
  на реальной базе и Linux/nftables. Подробности: [GEOIP_DATABASE.md](GEOIP_DATABASE.md).
- Без фильтрации прежний текст firewall должен оставаться неизменным.
  Отсутствующая/повреждённая база не должна молча отключать заданную фильтрацию.

#### Автоматическое обслуживание GeoIP-базы — согласовано 2026-09-10

- Первая загрузка и последующие обновления полностью автоматические: пользователю
  не нужно скачивать файлы, вводить ссылки, задавать расписание или обновлять базу
  командой. Механизм включён по умолчанию, работает и без перезагрузки VPS.
- Проверять обновления периодически в процессе панели, с задержкой и backoff при
  сбоях; не добавлять отдельный постоянно работающий демон. Интервал выбрать
  согласно частоте публикаций и ограничениям выбранного источника.
- Использовать заранее выбранный HTTPS-источник с проверенной лицензией и
  атрибуцией. Это HTTPS для загрузки базы, не HTTPS для внутренней панели.
- Загружать во временное хранилище с ограничениями времени и размера; проверять
  формат, обе семьи IP, наличие нужных стран и целостность. Контрольная сумма
  из того же источника не заменяет проверку доверия к самому источнику.
- Применять новый снимок атомарно, согласованно с текущими политиками клиентов;
  при ошибке загрузки, проверки или применения сохранять последний рабочий
  снимок и правила. Сериализовать обновление базы и изменение клиентских политик.
- Недоступный GitHub не должен останавливать VPN или молча снимать фильтрацию.
  Если базы ещё нет, не разрешать включение политики с ложным обещанием защиты;
  показывать понятный статус и автоматически повторять загрузку.
- В панели показывать источник, дату базы и состояние обновления. Новая версия
  базы не требует релиза панели или переимпорта клиентских профилей.
- Проверить штатное обновление, повреждённый/слишком большой ответ, тайм-аут,
  перезапуск в середине обновления, одновременное изменение политики и откат.
- Ориентир по удобству — автоматическое обслуживание geo-данных в 3x-ui.
  Источник-кандидат: Loyalsoldier/geoip, на который ссылается v2rayNG.
  Формат DAT нельзя передать nftables напрямую: выбрать CIDR-выгрузку либо
  проверяемое преобразование; Xray для этого не требуется. Окончательный
  источник не закреплён до проверки лицензии данных и полноты IPv4/IPv6.
  Ссылки: [v2rayNG](https://github.com/2dust/v2rayNG#geoip-and-geosite),
  [источники 3x-ui](https://github.com/MHSanaei/3x-ui/wiki/Configuration),
  [Loyalsoldier/geoip](https://github.com/Loyalsoldier/geoip).

### Стартовый экран панели — согласовано 2026-09-09

Статус: 2026-09-10 реализован первый локальный вариант, добавлены автоматические
проверки тайм-аута, восстановления и состояния сессии; ещё не опубликован.

- В стартовом HTML сразу показывать служебный экран: «Подключение к панели…
  Панель доступна только через Home VPN». Он не должен требовать успешного
  запроса к API для своего отображения.
- После успешного ответа сервера показывать форму входа либо панель согласно
  состоянию авторизации. При недоступности сервера показывать «Панель недоступна.
  Проверьте подключение к VPN» и кнопку «Повторить»; предусмотреть ограниченное
  ожидание ответа, а не бесконечную загрузку.
- Аналогичное уведомление нужно при потере связи в уже открытой панели.
  Не утверждать, что VPN точно выключен: сервер также может быть недоступен
  по другой причине.
- Допустимо использование обычного браузерного кэша для несекретной оболочки,
  но запуск вне VPN не гарантируется: если браузер не предоставит сохранённый
  HTML, вместо нашего экрана будет его собственная ошибка соединения.
  Установка сайта как web-приложения эту гарантию не даёт. Описать ограничение
  и проверить поведение в поддерживаемых браузерах при реализации.
- Не кэшировать профили, ключи, данные клиентов и ответы API; не ослаблять
  авторизацию. Service worker и HTTPS не добавлять. Не занимать и не
  резервировать порт 80; существующий порт панели сохраняется.
- Локализовать сообщения на все пять языков, проверить мобильный вид,
  доступность и RTL. Это экран загрузки с пояснением, не обещание офлайн-режима.

## 2026-08-27 — индикация после переключения профилей на одном телефоне

Статус: точная причина наблюдения не установлена; крайние случаи расчёта
исправлены в рабочей ветке, нужен повторный тест. Не считать доказательством постороннего
подключения или подтверждённым дефектом расчёта скорости.

### Как воспроизвести

1. Импортировать на телефон профиль `Home admin`, сохранённый после установки
   панели в сохранённых сообщениях мессенджера. Другие устройства этим профилем
   в момент проверки не пользовались.
2. Подключиться через `Home admin`, войти в панель и создать профиль `Honor 50`.
3. Сразу переключить AmneziaVPN на том же телефоне с `Home admin` на `Honor 50`.
4. Снова открыть панель.

Наблюдение с уточнением автора от 2026-08-29: оба профиля отображались активными;
у уже не используемого `Home admin` скорость колебалась примерно от
**170 до 230 бит/с**, а не была постоянной. Это именно бит/с, не байт/с;
предыдущая запись про 200 байт/с уточнена. Ненулевая меняющаяся скорость
отображалась после отключения, пока старый профиль сохранял статус активности.
Направление трафика, точная длительность и время после переключения пока
не зафиксированы — уточнить при повторном тесте.

Статус зависит от возраста последнего успешного handshake (окно 150 секунд),
а не от ожидания следующего handshake. Исправление устаревших результатов
не доказывает устранение именно этого наблюдения: нужен повторный тест
с сопоставлением серверных счётчиков. Исправления пока только в рабочей ветке.

### Что проверить при возобновлении работ

- Записать время переключения и последовательность показаний обоих профилей
  до и после него, включая обновление страницы панели.
- Сопоставить статус и скорость в UI с ответами API, серверными счётчиками
  RX/TX и временем последнего handshake отдельно для каждого peer.
- Проверить окно определения «в сети», интервал опроса и усреднения скорости:
  отличить недавнюю активность от продолжающейся передачи.
- Проверить сброс предыдущих выборок, корректную привязку счётчиков к peer,
  отображение устаревших данных и единицы bit/s против byte/s.
- При наличии реального роста счётчиков выяснить направление и природу
  трафика: остаточная передача, служебные пакеты или иной источник. Это
  гипотезы для проверки, а не установленная причина.
- Проверить, что после прекращения трафика скорость становится нулевой,
  а статус меняется по документированному тайм-ауту; при необходимости
  уточнить подписи UI, чтобы недавний handshake не означал гарантированное
  подключение устройства прямо сейчас.

Стабильный релиз не изменён; рабочие доработки описаны в срезе выше.

## 2026-08-28 — отдельное управление IPv4 и IPv6 клиента

Статус: идея для будущей версии, реализация не начата.

- Вместо «Клиент включён» рассмотреть два переключателя: IPv4 и IPv6.
- По умолчанию включать обе семьи, если сервер поддерживает обе. При отсутствии
  работоспособного серверного IPv6 показывать его недоступность с объяснением,
  а не обещать клиенту неработающее подключение.
- Четыре состояния: обе семьи, только IPv4, только IPv6, обе выключены
  (клиент отключён). Отобразить состояние явно; Home/Guest остаётся отдельным.
- Отключение обеих семей должно удалять peer из runtime. Сохранить защиту
  от отключения последнего доступного Home-клиента и потери доступа к панели.
- Согласовать адреса, AllowedIPs, DNS, nftables, discovery и экспорты профилей.
  У IPv6-only Home должен оставаться путь к панели и DNS через IPv6.

  провайдера: отдельно определить и проверить защиту от обхода туннеля.
- Изменение серверной политики не переписывает импортированный профиль в
  AmneziaVPN. Проверить, когда нужен повторный импорт, и явно сообщать об этом.
- IPv6-only не обещает доступ к IPv4-only сайтам без отдельного механизма
  трансляции. NAT64/DNS64 автоматически в объём этой задачи не включать.

## 2026-08-28 — автоматическое обновление после загрузки ОС

Статус: 2026-08-29 реализовано в рабочей ветке, без публикации релиза.
На новой установке с systemd или OpenRC включается по умолчанию и без вопроса.
Явное управление: `awg-easy-3 auto-update enable|disable|status|run`.
Существующая установка не получает boot hook до запуска нового установщика
или явной команды `auto-update enable`.

### Лёгкий механизм запуска

- После успешной установки и проверки работоспособности регистрировать
  штатное задание ОС для одного запуска обновления после каждой загрузки.
- На системах с systemd используется timer с `OnActiveSec=5min`, случайной
  задержкой до двух минут и oneshot service:
  отдельный постоянно работающий демон или контейнер не нужен.
- Сначала позволить штатно подняться текущему VPN, затем с небольшой задержкой
  проверить обновления. Не блокировать загрузку ОС или старт VPN ожиданием
  GitHub, реестра образов или сети. Возможный краткий разрыв при замене версии
  описать пользователю.
- Наличие network-online.target не гарантирует доступ к GitHub/GHCR:
  нужны ограниченное время ожидания и обработка отсутствия сети.
- Для OpenRC установлен собственный transient service: после пяти минут
  ожидания он один раз запускает ту же проверку и завершается. На других
  init-системах systemd, cron или новый демон не устанавливаются; выводится
  сообщение, что доступна ручная команда `awg-easy-3 update`.
- Это обновление при загрузке, не периодическое: без перезагрузок новые
  релизы сами по себе не устанавливаются.

### Безопасность обновления — до включения автозапуска

- Команда `update` больше не делает `git pull` ветки master: она выбирает только
  строгие теги `vMAJOR.MINOR.PATCH` из канонического репозитория. Prerelease
  игнорируются; tag, VERSION, схема состояния и закреплённый image обязаны
  составлять согласованный комплект.
- Не пересоздавать контейнер, если рабочая версия не изменилась.
- Сохранять клиентов, ключи, пароль, порты и настройки. Никаких автоматических
  reinstall, сбросов или несовместимых обновлений состояния.
- Новая версия и image полностью загружаются до fast-forward рабочей копии.
  Сбой загрузки ничего не заменяет; при неуспешном healthcheck Git и контейнер
  возвращаются на предыдущий commit и ранее загруженный image.
- Общая PID-lock исключает конкуренцию update, uninstall и reinstall. Она не
  перехватывается: после аварийного завершения осиротевший каталог в `/run`
  убирается перезагрузкой ОС. Автоматический запуск пропускает намеренно
  остановленную панель и не поднимает её сам.
- Журналировать версии и результат без паролей, ключей и vpn://-ссылок.
- Предусмотреть понятные включение/выключение и статус автозадания, а также
  его удаление при деинсталляции только для объектов AWG-Easy 3.
- Полевые проверки перед релизом: повторная загрузка, отсутствие сети, недоступный реестр, сбой
  нового контейнера, отсутствие обновлений, сохранение конфигов, ручной stop,
  параллельные команды и чистая деинсталляция.

Документация для проектирования:

- [Таймеры systemd](https://github.com/systemd/systemd/blob/main/man/systemd.timer.xml)
- [Готовность сети и запуск сервисов](https://systemd.io/NETWORK_ONLINE/)

Понятное DNS-имя панели исключено из текущего плана по просьбе автора.
Часть записей реализована в рабочей ветке согласно статусам выше.
Текущий стабильный релиз не меняется.
