# Регистрация Ячейки: первый этап реализации

Актуально 2026-09-15: прямой TLS-обмен регистрации и настроек проверен между двумя
VPS, включая реальное применение AWG. Есть отдельный тестовый запускатель;
продуктовая служба, установщик и интерфейс пользователя ещё не подключены. Разделы ниже
описывают последовательные этапы прототипа, а не возможности текущего релиза.

Это внутренний фундамент, а не доступная пользователю функция релиза.
Модули `CellInvitation.js`, `CellRegistration.js` и `CellEnrollmentStore.js` пока не подключены к HTTP,
установщику и состоянию VPN.

## Граница доверия

Приглашение — секрет предъявителя, передаваемый владельцем доверенной Ячейке.
Код содержит адрес и порт будущего служебного транспорта, закреплённый публичный
ключ Основного узла, идентификатор приглашения, срок и случайный секрет 256 бит.
Base64url скрывает привычный вид адреса, но не шифрует его. Код нельзя логировать.
Это собственный формат, не профиль AmneziaVPN и не предоставление прав Home.

Основной узел хранит только SHA-256 секрета и ожидающую запись с ролью Ячейки.
Секрет не выбирается пользователем. Сравнение проверочных значений — constant-time.
Публичный ключ в приглашении должен проверяться будущим защищённым транспортом;
сам код не доказывает подлинность без доверенного способа его передачи.

## Переходы

- `pending` → `consumed`: секрет доказан, отдельная регистрация проверена,
  постоянный публичный ключ Ячейки закреплён.
- `pending` → `blocked`: секрет доказан, но регистрация недопустима.
- `pending` → `revoked`: отзыв владельцем.
- Истечение срока запрещает регистрацию; оно не требует фонового таймера.
- Пакеты с неверным секретом ничего не меняют. Сетевой обрыв сам по себе не
  является недопустимой регистрацией и не блокирует приглашение.
- Повтор успешного запроса с тем же request ID и ключом возвращает прежний
  результат (потерянный ответ); другая регистрация по погашенному коду запрещена.
  Отзыв уже зарегистрированной Ячейки будет отдельным жизненным циклом Ячейки.

## Обязательства следующего слоя

Добавлен Ed25519 proof-of-possession через встроенный `node:crypto`.
Подписывается фиксированный массив с отдельным контекстом протокола: ID
приглашения и запроса, оба публичных ключа, время и SHA-256 секрета.
`completeSigned` проверяет подпись до перехода состояния; ключ Основного узла
передаётся из локальной доверенной конфигурации. Поле `registrationValid` из
сети не используется. Ключи управления отдельные, не AWG-ключи клиентов.

Запрос действует менее пяти минут; будущее время допускается максимум на 30 секунд
из-за расхождения часов независимых VPS. Этот допуск не продлевает срок уже
устаревшего запроса; синхронизация часов всё равно нужна. Такой же допуск действует
для подтверждения регистрации и poll/ack. Для повтора после потери ответа нужно сохранить исходный
запрос: новый request ID не считается повтором. Срок приглашения также действует.
Повреждённая подпись не меняет состояние приглашения: это ещё не завершённый
аутентифицированный обмен. Блокировка за недопустимую регистрацию остаётся
внутренним переходом, не реакцией на произвольный пакет.

Подпись **не шифрует секрет**. Передача запросов, включая через посредника,
допускается только после добавления защищённого сквозного транспорта с проверкой
ключа Основного узла. Пока нет сетевого listener, постоянного хранения приватных
ключей управления в установщике. Публичное включение запрещено
до реализации этих частей и проверки модели доверия целиком.

### Постоянная идентичность управления

`ControlIdentityStore` добавлен как отдельный внутренний компонент. Создание
явное, только для первой установки: `create(role)`. Запуск должен использовать
`load(role)`; отсутствующий, повреждённый ключ или чужая роль — ошибка, не повод
автоматически создать новую идентичность. Проверяется соответствие пары Ed25519.
Файл приватный (0600 на Linux), временный файл синхронизируется и публикуется
через hard link без перезаписи существующего файла. Файловая система должна
поддерживать hard links; небезопасного fallback с перезаписью нет.

Приватный ключ хранится незашифрованным с ограничением файлового доступа,
как служебный секрет для автономного запуска, не выводится в UI. Родительский
каталог должен принадлежать службе и быть недоступен для записи посторонним.
Операции пока не подключены к установщику. Linux-проверка прав требует отдельного
запуска на Linux; тест на Windows её пропускает. При аварии после публикации
файл может уже существовать: следует загрузить его, а не заменять новым.

### Ответ регистрации

`CellRegistrationService` объединяет загрузку идентичности, проверку запроса,
постоянную запись и подпись подтверждения — именно в таком порядке. Ответ
Ed25519 имеет отдельный контекст подписи, статус `registered`, ключи обеих сторон,
ID приглашения/запроса, время и хеш подписанного содержимого запроса. Секрет
приглашения в ответ не включается. Ячейка проверяет ключ из доверенного приглашения,
а не принимает ключ из ответа как новый источник доверия.

Повтор исходного запроса после потери ответа возвращает новое подтверждение
той же регистрации в пределах срока запроса и приглашения. Подтверждение означает
только регистрацию ключа: не установку VPN, применение маршрутов или доступность
выхода. Сетевой транспорт по-прежнему не подключён; подписи не заменяют шифрование.

### Граница входящих сообщений

`CellRegistrationHandler` принимает только Buffer до 2048 байт с корректным UTF-8
и точной схемой регистрации v1. Дополнительные поля не допускаются. Ошибки наружу
обезличены: без путей файлов, секретов и признака существования приглашения.
Обработчик не исполняет никаких административных команд.

Один экземпляр на контроллер для всех транспортов: не более четырёх параллельных
обработок, burst 16 и пополнение одного запроса в секунду по монотонным часам.
Очереди ожидания нет; некорректные сообщения также расходуют бюджет. Эти пределы
предварительные и требуют нагрузочного теста. Общий лимит не гарантирует защиту
доступности от DoS, а ограничивает работу обработчика.

Будущий транспорт обязан ограничить объём **до** накопления Buffer, количество
соединений, срок чтения и аутентификацию защищённого канала. Сам обработчик не
создаёт listener и не отменяет начатую запись по таймауту. Подключение к публичному
незашифрованному порту недопустимо.

### Прямой шифрованный транспорт (локальный прототип)

`CellRegistrationTransport` реализует TLS 1.3 с отдельным ALPN и одним ограниченным
JSON-сообщением на соединение. Ключ сертификата Ed25519 должен совпадать с ключом
Основного узла из приглашения. Клиент проверяет этот pin после handshake **до**
отправки секрета; публичный CA и совпадение hostname не являются источником доверия.
Сертификат служит оболочкой закреплённого ключа, его срок не используется как
механизм отзыва. Отзыв/смена ключа требуют отдельного протокола.

Это служебный TLS, не перевод веб-панели на HTTPS. Порт автоматически не открывается:
экспортируется фабрика сервера без вызова listen. Пока сертификат передаётся извне;
выдача/хранение сертификата, установщик, firewall и запуск службы ещё не подключены.
В тестах сертификат создаёт OpenSSL (`AWG_TEST_OPENSSL` может переопределить путь).
Проверены реальный обмен по loopback, отказ чужому ключу до передачи секрета,
превышение размера и зависание peer до TLS-handshake.

Срок соединения ограничен целиком, максимум соединений по умолчанию 16.
Резервная ретрансляция ещё отсутствует: она должна переносить сквозной защищённый
канал, а не завершать TLS на посреднике. Этот прототип не готов к публичному выпуску.

### Автоматическая подготовка сертификата

`ControlCertificateStore.ensure()` создаёт самоподписной сертификат локальным
OpenSSL из существующей идентичности Основного узла (365 дней), повторно использует
действующий и продлевает при остатке не более 30 дней. Продление не меняет ключ
и не требует новых приглашений. Это проверка при подготовке сервера, не фоновый
таймер и не hot reload. Повреждённый или чужой сертификат не заменяется молча.
При сбое генерации существующий файл сохраняется; запись нового атомарная.

Приватный ключ временно записывается в каталог 0700, файл 0600; после операции
временные файлы удаляются. Аварийное завершение процесса может оставить временный
каталог: уборку при старте ещё нужно включить в эксплуатационный цикл. Каталог
службы должен быть доступен для записи только владельцу. Один процесс-владелец,
как и у хранилища регистрации. OpenSSL запускается без shell, с timeout 15 секунд
и без ключа в аргументах. Никаких внешних CA, DNS-проверок и сетевых запросов.

`prepareRegistrationEndpoint` объединяет существующую идентичность, сертификат,
хранилище, проверку запросов и TLS-сервер. Самостоятельно не вызывает listen.
Интеграционный тест проводит регистрацию через настоящий loopback TLS с этими
компонентами. Подключение к установщику, доставка OpenSSL, служба, firewall,
сохранение результата на стороне Ячейки и эксплуатационные тесты ещё впереди.

### Состояние подключения Ячейки

`CellConnectionStore.begin(code)` сначала сохраняет точный подписанный запрос
в файле 0600. `resume()` отправляет его через проверяемый TLS-транспорт и после
проверки подтверждения атомарно записывает состояние `registered` с адресом,
ключами и ID приглашения, уже без секрета и исходного запроса. Перезапуск в
состоянии registered не повторяет регистрацию. Это не означает наличия VPN-связи.

После обрыва или ошибки сохранения подтверждения повторяется прежний запрос.
Действуют оба срока: пять минут для запроса и срок приглашения. Долгий простой
не обходится автоматической перепривязкой: нужен будущий операторский сценарий
восстановления незавершённой регистрации. Сейчас неизвестное/повреждённое состояние
не перезаписывается, новое приглашение поверх существующего не принимается.
Полноценный контроль доступности, применение правил и автономная работа ещё впереди.

Хранилище однопроцессное, как на Основном узле. Секрет pending хранится локально
для повторной отправки; удаление из нового JSON не является гарантированным
стиранием старых блоков носителя/снимков/резервных копий. Каталог должен быть
недоступен посторонним. Протестирован также реальный TLS-обмен с обоими хранилищами.

### Версии настроек после регистрации — локальный механизм

`CellSettings` подписывает снимок настроек Ed25519 с отдельным контекстом,
ключами отправителя/получателя и положительным монотонным номером revision.
Размер payload ограничен 256 КиБ. Содержимое подписано как точная JSON-строка.
Подпись не шифрует клиентские данные: доставка должна быть по защищённому каналу.

`CellSettingsReceiver` атомарно сохраняет отдельно полученную и последнюю
подтверждённо применённую версии. Отвергает старые версии и конфликт одинаковых
номеров. Повтор успешной версии не вызывает повторное применение. Неудачное
применение не продвигает applied; при старте `restoreApplied` передаёт адаптеру
последнюю успешную версию. Незавершённую новую версию автоматически не применяет.

Это внутренний механизм с обязательными адаптерами validate/apply, **не готовая
доставка или применение VPN-конфигурации**. Тесты применения используют имитацию.
Реальный адаптер обязан проверить полную схему, обеспечить идемпотентность и
откат частично выполненного изменения AWG/nftables. Если runtime изменился, а
сохранение applied упало, подтверждения не будет; повтор/восстановление должны
быть безопасны. Подписанное сетевое подтверждение applied пока не реализовано.
Смена полномочий при restore, хранение счётчика на Основном узле и доставка
снимков по служебному транспорту также ещё не подключены.

### Схема назначений клиентов v1

`CellSettingsSchema` — стандартная проверка получателя: только явные ID, публичные
AWG-ключи/опциональные PSK, одиночные адреса IPv4/IPv6, Home/Guest, булевы флаги
семей и GeoIP-политика. Приватные клиентские ключи, команды shell, nft-текст,
неизвестные поля и неизвестные режимы не принимаются. Нормализованная схема
передаётся адаптеру применения. Пустая Ячейка и Ячейка без Home допустимы.
Не более 1000 назначений, ID/ключи/адреса уникальны; IPv6 сравнивается численно.

Это пока **схема назначений**, не полная топология: выбор входов/выходов, межсерверные
маршруты и редиректы GeoIP ещё не добавлены. Нельзя использовать её для включения
реальной Ячейки без следующих проверок локального контекста (принадлежность адресов
VPN-подсетям, отсутствие конфликтов с сервером, доступные семейства и интерфейсы).
Генератор основной панели требует Home и выдаёт клиентские профили; нужен отдельный
адаптер Ячейки, не ослабление существующих проверок основной панели.

### Генерация и применение локальной Ячейки

Добавлен `CellArtifacts`: проверяет принадлежность адресов каноническим VPN-подсетям,
конфликт с адресом сервера, IPv4 network/broadcast, доступность семей; генерирует
AWG и nftables без клиентских приватных ключей. Внутренний headless-режим nftables
разрешает пустую/Guest-only Ячейку и закрывает её локальные сервисы от VPN-клиентов.
Стандартная проверка обязательного Home у Основного узла сохраняется.

`CellRuntimeAdapter` использует существующий RuntimeApplier, но перед изменением
ставит отдельную таблицу `awg_easy_3_cell_guard`, блокирующую только трафик AWG-
интерфейса. После полного успеха удаляет её. При любом неопределённом исходе
guard остаётся: это остановка трафика, не молчаливый обход ограничений. Retry или
restore успешного снимка снимает guard только после применения. Удаление guard
должно также войти в будущую деинсталляцию Ячейки. Нельзя размещать этот прототип
рядом с другой установкой AWG-Easy, использующей те же объекты.

Поддерживается пока только вход/выход на одной Ячейке; Home между серверами,
policy routing и перенаправление по GeoIP ещё не реализованы. Синтаксис nftables
проверен на Linux в отдельном namespace, порядок вызовов/ошибки runtime — имитацией.
Для проверки реальных AWG-команд нужна среда с AWG; готовность к релизу не заявляется.

### Доставка настроек, подтверждения и цикл агента

`CellSettingsPublisher` хранит текущий подписанный снимок и возрастающую revision
отдельно для каждой Ячейки; имя файла выбирает доверенная служба, не удалённый
запрос. Новая публикация сбрасывает подтверждение. `CellSettingsAck` связывает
подпись Ячейки с ключами сторон, revision и хешем снимка; старый ответ не может
подтвердить новый снимок. Подтверждение создаётся из сохранённого applied-состояния.

`CellControlProtocol` поддерживает только poll/ack, отдельный контекст подписи и
пятиминутный срок запроса. Повторы poll безвредны, ack идемпотентен. Эти полномочия
не распространяются на будущие удаление/restore-команды. `CellControlService`
проверяет сохранённую регистрацию до доступа к снимкам; не возвращает ключи
других Ячеек. Для прототипа выбран pull: Ячейка инициирует TLS к Основному узлу,
отдельный ALPN `awg-easy-3-control/1`. Это отдельный тестовый endpoint; объединение
служебных портов/настройки установщика ещё не решено в коде. Ответ проверяется по
requestId и подписи снимка; TLS закреплён за ключом зарегистрированного узла.

`syncCellSettings` применяет полученный снимок и отправляет ack только после
успеха. `CellAgent` сначала вызывает restoreApplied, затем синхронизирует без
перекрывающихся операций. Интервал 15 секунд, backoff до 60 секунд. Сбой сохраняет
время последнего подтверждения и не останавливает VPN; stop останавливает только
управление. Обработчик статуса не может сломать цикл. При restore-ошибке запуск
прерывается явно. Ошибка sync может быть сетевой, валидационной или применения,
поэтому помечается sync-failed, а не объявляет недоступность сервера доказанной.

Прямой цикл проверен настоящим TLS на loopback с постоянными хранилищами;
применение в этом тесте имитируется, отдельно проверен настоящий AWG в WSL
(CELL_WSL_TESTS.ru.md). Перед публичным включением ещё нужны ограничение частоты
control-запросов (сейчас concurrency), CLI/служба/отзыв/сетевые сбои на VPS.

Перед вызовом завершения регистрации проверить доказательство владения ключом
Ячейки и совместимость протокола. Булев результат проверки — внутренний аргумент,
не поле, которому разрешено доверять в запросе из сети. Ограничить размер входа
до JSON-разбора, частоту запросов и число приглашений.

Все переходы сериализовать и атомарно сохранять **до** ответа и выдачи полномочий.
Чистые функции приглашений возвращают новое состояние. `CellEnrollmentStore`
сериализует изменения и записывает отдельный JSON через временный файл 0600,
fsync и rename; на Linux также синхронизирует каталог. Ответ выдаётся после записи.
При ошибке после rename результат может уже быть сохранён: повтор того же запроса
читает файл заново и возвращает прежний результат, без второй регистрации.
Повтор запроса не должен продлевать срок или создавать вторую Ячейку.

Хранилище рассчитано на **один процесс-владелец**, экземпляры внутри процесса
разделяют очередь по абсолютному пути. Межпроцессной блокировки пока нет:
будущие CLI/HTTP должны обращаться к работающему контроллеру, а не независимо
перезаписывать файл. Не использовать разные алиасы/симлинки одного пути.
Повреждённое или неизвестное состояние отклоняется, а не заменяется пустым.
Ограничение: 1024 записи и 1 МиБ. Очистка старых приглашений и отдельный полный
жизненный цикл Ячейки ещё нужны; погашенная запись сейчас сохраняет её ключ.

Прямой и резервный каналы должны использовать одинаковую авторизацию. Резервный
посредник не получает секрет приглашения или клиентские ключи. Выбор защищённого
транспорта, отдельные подписанные команды с защитой от повторов,
регистрация через установщик, маршрутизация и DHT ещё не реализованы.
