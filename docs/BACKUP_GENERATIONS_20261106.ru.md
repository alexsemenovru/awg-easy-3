# Создание backup и поколения восстановления — 6 ноября 2026

Состояние ветки разработки, не объявление готовности restore.

## Продуктовая цепочка создания

В панели появился раздел резервной копии: повторная проверка текущего пароля
и/или TOTP согласно выбранному режиму входа, архив и отдельный ключ.
POST `/api/v1/backups` требует действующую сессию и тот же origin, не кешируется;
параллельные запросы сериализованы, частота ограничена одной попыткой в минуту.
Секрет не сохраняется в браузерном хранилище. При закрытии окна/выходе ссылки
Blob отзываются, поля очищаются. Интерфейс переведён на все пять языков.

Панель удерживает общую очередь изменения состояния, а Main — installation
flock. Обработчики AWG-регистрации и управляющих RPC теперь используют тот же
flock, как и согласование Ячеек. Сам VPN при создании архива не останавливается.

Архив сохраняется в `data/backups/<id>/` для одиночной панели либо
`cell-data/backups/<id>/` при включённом Main-компоненте:

- `configuration.awgbackup`: AES-256-GCM, случайный отдельный ключ;
- `recovery-key.txt`: отдельный ключ расшифрования, приватные права;
- `grant.json`: публичная подписанная проверочная запись для Main/Cell.

Файлы и записи каталогов проходят fsync **до** публикации нового поколения.
При сбое сохранения прежнее поколение не отзывается. Если HTTP-ответ потерян,
копия остаётся на сервере: интерфейс просит проверить это перед новой попыткой.
Автоматической очистки старых архивов нет.

Инвентарь исключает чужие файлы, логи, контакты DHT, журналы владения объектами
ядра и metadata уже отозванных Ячеек. Семантическая проверка дополнительно
сверяет X25519-пары панели/клиентов/Main, подписи настроек, реестр Ячеек,
базу/ревизию постоянного control-плана, объявления data-ключей и data-планы,
заново построенные из проверенных дескрипторов. Архивные команды не исполняются.
Незавершённый переход постоянного канала требует сначала завершить согласование.

## Поколение и подтверждения

В зашифрованном архиве находится отдельная Ed25519-пара восстановления.
Main публикует подписанный grant с поколением, идентификатором, SHA-256 архива
и публичной частью этой пары. Приватная часть не передаётся Ячейкам.

Ячейка получает grant по существующему AWG control RPC, сохраняет и подписывает
подтверждение. Main принимает его только для точного архива/поколения и Ячейки,
которая включена в этот архив. Добавленная позже Ячейка не получает фиктивного
права восстанавливаться из более старой копии. В UI видны номер поколения и
ожидание/получение подтверждения без публичных ключей или адресов.

Ячейка не принимает более раннее поколение или другое содержание при том же
номере. Недоступная Ячейка сохраняет прежнее поколение до получения нового:
невозможно отозвать её локальные полномочия без доставки сообщения.

## Основа takeover и граница готовности

Проверены свежий одноразовый challenge Ячейки, точная привязка к архиву,
подпись отдельным recovery-ключом и сохранение consumption до смены управления.
Два параллельных восстановления не могут потребить один grant дважды;
перезапуск и повторная доставка grant не сбрасывают consumption.

Исторический ключ подписей настроек сохраняется для автономного чтения старых
подписанных ревизий. После takeover ответы управления должны дополнительно
подписываться новым live authority-ключом восстановленного Main. Старой копии
исторического ключа недостаточно для таких ответов. На новом Main этот ключ
хранится отдельно как `authority.json` и не включается в следующий backup.
Все обычные Cell control-запросы проверяют закреплённую live authority.
TLS/сертификаты не добавлены.

**На момент первого этапа ещё не завершено:** запуск takeover через продуктовый сетевой путь, переход
к новому endpoint и DHT-идентичности, согласованный переход сохранённых ревизий
на новую authority, транзакционная активация restore с предыдущим снимком.
Владение архивом и его ключом пока не является готовой командой переноса VPS.
Эти части нельзя подменять ручным копированием журналов ядра или объявлять
готовыми только по тестам криптографических компонентов.

### Дополнение второго этапа 6 ноября

Управляющий RPC теперь выполняет одноразовый обмен `recover` при смене live
authority. После проверенного proof Ячейка закрепляет новую authority и номер
поколения также в постоянной записи подключения. Старые ответы и старые
подтверждения backup не проходят. Новая Ячейка получает live authority сразу
в подписанной AWG-регистрации v4; прежние регистрации v2/v3 остаются читаемыми.

Журналы настроек и маршрутов учитывают поколение authority: восстановленная
копия может начать новую последовательность ревизий, не ослабляя запрет
повторных/конфликтующих ревизий внутри поколения. При ошибке применения
сохраняется прежняя успешно применённая версия для автономного запуска.
Потеря записи recovery не разрешает повторно использовать уже потреблённое
поколение из-за дополнительного закрепления в записи подключения.

Добавлен продуктовый адаптер назначения восстановленного endpoint. Он
проверяет AWG-владение и точные UDP source/destination tuples для control/data,
устанавливает только собственные DNAT-таблицы и оставляет пинованные конфиги
AWG прежними. Перед изменениями активируется пользовательский traffic guard;
его обычное снятие остаётся за проверенной маршрутизацией. Технический CONTROL
redirect имеет больший приоритет и не переносит data в служебную сеть. DNS-ответ
фиксируется по хешу подписанного takeover. Повтор без изменений ничего не
переустанавливает; остановка удаляет только проверенные собственные отображения.

Настоящие AWG control/data-интерфейсы в разных network namespace подтвердили
перенос назначения на новый Main IP при недоступном старом адресе, успешный
подписанный RPC по обеим плоскостям и неизменность исходных AWG Endpoint.
Это проверка транспорта с тестовым proof, **не полный продуктовый restore**.
Текущий адаптер переноса поддерживает внешний IPv4-транспорт; IPv6 внутри VPN
от этого не ограничивается. Внешний IPv6 endpoint пока требует отдельной работы.

После второго этапа по-прежнему нужны подготовка новой установки из архива, предыдущий снимок,
транзакционная активация/откат и сквозной запуск Main+Cell после restore.

### Подготовка новой установки и первый запуск

`restore-cli.js prepare ARCHIVE KEY_FILE NEW_HOST_STATE OUTPUT` расшифровывает
и семантически проверяет архив до записи файлов. Все пути абсолютные; входные
файлы приватные, ограниченного размера, без hardlink/symlink на Linux. Ключ
передаётся файлом, не значением в аргументе. Вывод содержит только результат,
количество профилей/Ячеек и поколение; ошибки точки входа не печатают JSON входа.

Новый приватный workspace сохраняет профили, ULA и действующий TOTP, обновляет
cookie, использует адресные настройки новой установки. Неиспользованные
приглашения закрываются. Последний зафиксированный набор control-peer становится
новой базой; прежние owner UUID и журналы ядра не импортируются. Создаются новая
live authority, recovery proof material и разрешение первого bootstrap-запуска.
`restore-cli.js inspect OUTPUT` повторно сверяет файлы, bindings, получателей и
состояние recovery. Изменение подготовленных данных делает проверку неуспешной.

Первый запуск Main с импортированными Ячейками допускается только после сверки
этого разрешения и обычной проверки свободных ресурсов. Разрешение удаляется
после создания новых долговечных bootstrap-журналов. Потеря журнала в обычной
установке не превращается в разрешение пересоздать интерфейсы.

В одноразовом контейнере без внешней сети проверены: зашифрованный архив с двумя
Ячейками → новый workspace → настоящий продуктовый `host.resume()` → создание
AWG bootstrap/control и двух control-peer → повторный запуск с тем же новым
владением. 8/8 проверок, без пропусков. Обычный полный Ubuntu-набор: 891 успешно,
1 отдельный контейнерный сценарий пропущен; nft kernel checks включены.

**Граница готовности:** CLI пока только подготавливает, `activated:false`.
Не завершены предыдущий снимок текущей установки, транзакционное переключение
её каталогов/host bindings с откатом и сквозной запуск Main+Cell именно через
эту команду. DHT locator/fencing и внешний IPv6 endpoint также требуют проверки.
Не объявлять эти проверки полной готовностью пользовательского restore.
